HMWK 2: Ethereum Wallet Pipeline

Hashing, Key Derivation and Cryptographic Primitives

1. Temporal and Historical Context

The evolution of Ethereum's cryptographic pipeline is built upon a decades-long progression of mathematical discoveries and interoperability standards.

1977
RSA: Pioneer of public-key cryptography. Replaced in the blockchain world by Elliptic Curves, which offer the same security with much shorter keys (256-bit ECC vs 3072-bit RSA).
2001
SHA-2: Standardized by NIST (includes SHA-256 and SHA-512). Used historically in Bitcoin for mining and derivation, but theoretically vulnerable to length extension attacks.
2012
BIP-32: Revolutionizes wallet management by introducing the HD (Hierarchical Deterministic) structure. Allows deriving an entire tree of keys from a single seed using HMAC-SHA512.
2013
BIP-39: Introduces the Mnemonic Code. It operates in two distinct phases: (1) raw entropy + SHA-256 checksum generates the mnemonic sentence (12-24 words); (2) the mnemonic sentence + optional passphrase generates the final 512-bit seed via PBKDF2-HMAC-SHA512 with 2048 iterations.
2014
BIP-44: Standardizes derivation paths for HD wallets (e.g., m/44'/60'/0'/0/0 for Ethereum), ensuring multi-account/multi-currency interoperability.
2015
SHA-3 (NIST): Standardized by NIST, based on the Keccak function (winner of the hashing standard competition).
2016
EIP-55: Introduced on Ethereum: a backward-compatible checksum that capitalizes the letters of the hexadecimal address. It offers on average ~15 bits of redundancy: the probability of a random typo passing unnoticed is approx 0.0247%.

2. Keccak-256 vs Standard SHA3-256

Although derived from the same algorithm based on the Sponge Construction, Keccak-256 (used in Ethereum) and SHA3-256 (the NIST standard) are not identical. Ethereum launched before NIST finalized the definitive standard. NIST modified Keccak's original padding byte (changing it from 0x01 to 0x06) for domain separation purposes. Consequently, while sharing the same internal architecture and security guarantees, they produce completely different outputs for the same input.

3. Separation of Concerns: Roles and Statistical Properties

The Ethereum ecosystem uses multiple orthogonal primitives because a single algorithm cannot simultaneously guarantee human usability, deterministic hierarchical derivation, algebraic digital signatures, and irreversible compression.

  • Key Generation (BIP-39): Generates entropy and the seed.
    Statistical Property: Pure uniformity (CSPRNG). The output must be unpredictable. Any statistical bias would compromise the seed's initial unpredictability.
  • Key Derivation (BIP-32 / BIP-44): Hierarchical management of the key tree.
    Statistical Property: Pseudorandomness (HMAC). By modifying the derivation index, the generated child keys must not show any visible linear correlation, despite remaining mathematically deterministic.
  • Public Key Crypto (secp256k1): Authentication and ECDSA Signatures.
    Statistical Property: Algebraic Hardness (ECDLP). No true bitwise Avalanche Effect. It preserves the mathematical group structure required to sign, but reversing the equation Q = kG is computationally intractable in polynomial time.
  • Hashing (Keccak-256): Compression and cryptographic abstraction. Derivation follows the explicit formula:
    address = "0x" + Keccak-256(uncompressed_pubkey[1:])[12:]
    (where [1:] strips the 0x04 prefix and [12:] takes the last 20 bytes).
    Statistical Property: Avalanche Effect and Collision Resistance. Destroys the curve's algebraic structure. Flipping 1 single bit in the public key chaotically inverts ~50% of the hash bits.
  • Encoding (EIP-55): Error prevention and UX improvement.
    Statistical Property: Error Detection. No intrinsic cryptographic value. It exploits the underlying hash's avalanche effect to invalidate the string if a user mistypes a character.

4. Fundamental Distinctions & Practical UX

When experimenting with commercial wallets (e.g., MetaMask, Rabby, Rainbow), the user is completely isolated from the underlying cryptographic complexity: they only see the mnemonic phrase and the final EIP-55 address. Internally, the software executes the entire pipeline (BIP-39 → BIP-32 → BIP-44 → secp256k1 → Keccak-256).

  • Key Generation vs Key Derivation: Generation requires creating pure, random entropy from scratch. Derivation takes that starting point (the seed) and uses deterministic mathematical functions to calculate infinite child keys in a structured way.
  • Public-Key Cryptography vs Hashing: Asymmetric cryptography is an algebraic map (one-way function based on the discrete logarithm) that allows signature verification. Hashing takes data of any size and compresses it into an irreversible fixed-length string, without keys and without preserving any mathematical structure of the input.
  • Checksum/Encoding vs Cryptography: EIP-55 does not encrypt or hide data. It simply adds a layer of visual redundancy (uppercase/lowercase) to allow software to catch typos before funds are sent to the wrong address.

5. The Role of the Final Hash and Quantum Resistance

It is often mistakenly believed that hashing the public key with Keccak-256 to obtain the address serves to protect Ethereum from quantum computers. This is incorrect. Shor's algorithm (a quantum attack) solves the discrete logarithm problem, fundamentally breaking the secp256k1 curve and forging ECDSA signatures; hiding the public key behind a hash protects funds only until the first outgoing transaction is sent (at which point the public key is inevitably revealed to the entire network to validate the signature).

Instead, Keccak is primarily used for spatial compression (reducing the uncompressed public key from 64 bytes to the 20-byte address) and to add a standardized abstraction layer. Against hash functions like Keccak, quantum computers (via Grover's algorithm) offer only a quadratic speed-up, which is easily countered and rendered harmless by the algorithm's 256-bit length.
